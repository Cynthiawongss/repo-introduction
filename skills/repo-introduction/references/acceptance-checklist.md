# Acceptance checklist

Mark each as passed / failed / not run / not applicable. This list is not itself evidence of testing.

| Check | Pass when |
|---|---|
| Facts | Capabilities, input/output and how to run it trace to the project; plans are separate from what exists |
| First screen | Name, language switch, one-line value and a cover that helps understanding |
| Example | Input, constraints, what happens, concrete output, honest verification status |
| UI labels and numbers | Every bold label and every count found in the source (`check_readme.py --source`) |
| Two languages | Same numbers, capabilities, limits, commands, paths, images and versions; each reads naturally |
| Cover: subject | The user confirmed the subject fits, separately from liking the style |
| Cover: honesty | A concept image is labelled and never described as a product screenshot |
| Cover: quality | Opened at full size; no callout crossing text, nothing touching the frame edge, text legible on a phone |
| Screenshots | Real app, finished state (no `MOVING`), fictional data, same viewport, right language and theme, each opened |
| Cover source | Script or HTML committed with a render command; selected file identical to the approved candidate |
| Layout | Headings, paragraphs, tables and code blocks read well on GitHub; long commands are in code blocks |
| Paths | Relative links and images exist; no local absolute or temporary paths |
| Get started | Reproducible in the stated environment; steps not run are labelled |
| Limits | No overstated automation, platforms, performance, security or consistency |
| Public material | Only project files; no credentials, private chat, real personal data or caches |
| Remote | Only within current authorisation; account, visibility, branch, README, images and About verified after pushing |

Record visual checks and functional checks separately. Delivery note: file list, checks passed, checks not run and why, selected cover number, git state, links.
